Solo project · Go · Google Cloud · May–June 2026

kalshiflow

A managed-services pipeline on Google Cloud that recorded Kalshi prediction-market WebSocket feeds (every orderbook change, trade, lifecycle event, and settlement) into BigQuery and a Parquet archive for offline backtesting. I designed, built, and ran it in production on my own.

Architecture

One always-on Go worker holds the WebSocket session. Everything downstream is managed services configured in Terraform, so there is no stream processor or database to operate.

Control plane

Series discovery

A 6-hourly job refreshes the Kalshi catalog and writes the desired series set to a GCS JSON object with If-Generation-Match. The worker polls it every 60 s and re-subscribes in place, with no redeploy.

Design decisions

Each of these was settled with a measurement, not a guess.

Protobuf envelope on the wire

I cut the Pub/Sub wire format over from JSON to a schema-registered protobuf Envelope (2026-05-04), which roughly halved row size (~270 B → ~135 B). The BigQuery payload column became BYTES, and Parquet carries it unchanged.

Measure the filter before claiming the saving

Back-of-envelope math said a top-2-price filter on orderbook deltas would drop ~80% of volume. Replaying 286k real deltas through the bookkeeper showed ~45%, because activity concentrates at the top of the book. The design shipped on the measured number.

GCS JSON for control state, not BigQuery

BigQuery on-demand bills at least 10 MB per query, so polling it every 60 s for a tiny desired-set costs far more than the data justifies. A generation-checked GCS object does the same job inside the free tier.

Managed ingest, no stream processor

Pub/Sub → BigQuery subscriptions plus a daily export job replaced a custom ingest service. The only always-on compute is the WebSocket worker.

Know the platform's billing floor

A Cloud Run worker pool with always-allocated CPU has a floor of 1 vCPU / 512 MiB. Retiring a sidecar container saved $0 of compute, not the ~$8/mo a naive estimate predicted. I re-checked the cost against the Cloud Billing Catalog before stating it.

Every cost claim cites a SKU

Monthly cost was ~$17, almost all of it the worker pool (CPU SKU 77E7-D935-BA67 + memory 967D-19B3-F10F, us-east4, verified 2026-06-10). Everything else stayed under free-tier thresholds, and each line item is listed in the cost breakdown.

Incidents and what they taught

The bugs that made it to production, and the detection I built so each one would not recur silently.

Silent WebSocket stall

2026-05-05 · ~58 minutes

The TCP connection stayed open while Kalshi stopped sending data, so no reconnect fired. The giveaway was that snapshot rows arrived at a perfectly flat 796/min: the bookkeeper's heartbeat was the only output.

Two independent watchdogs: a ping/pong deadline at the socket layer and a 90 s trading-frame deadline at the application layer, each with its own counters and a per-tick liveness heartbeat.

Watchdog masked by lifecycle chatter

2026-05-08

Exchange-wide lifecycle events at market rollover kept resetting the data-stall deadline while the tracked markets had gone silent.

Frames are sorted into trading and lifecycle buckets, and only trading frames count as liveness.

Unsubscribe flood at rollover

2026-05-08 12:01 UTC

Explicit unsubscribes for settled markets raced Kalshi's own server-side retirement and produced a flood of code:7 Unknown subscription ID errors.

Stop unsubscribing: rely on server-side auto-retire and evict locally, behind an env kill-switch that can restore the old behavior.

Overnight trading famine

recurring, 07–10 UTC

In the pre-dawn US window the feed can go many minutes without a single trade or book change. The watchdog correctly trips and cycles, and no data is lost.

Not every alert is a bug. The runbook gives a four-signal fingerprint that separates expected famine from a real stall.

Restart poisoned all metrics for ~25 h

2026-05-30 → 31

An in-place restart reused the OpenTelemetry resource identity, so Cloud Monitoring rejected every cumulative point with an earlier start time. Ingest was fine, but the dashboards went dark. The alert meant to catch it matched zero logs because it used the wrong label and payload field.

A per-boot node_id for each process, a unit test that stops service.instance.id from silently changing the resource type, and a repaired alert filter.

Pub/Sub → BigQuery silent hang

early build

Sending a nested JSON object into a BigQuery JSON column made the direct subscription retry forever, with no error, no dead-letter entry, and no rows.

A parallel pull subscription is the check that always works. The protobuf/BYTES cutover later removed this failure mode entirely.

Reusing it as a reference architecture

The repository is a scrubbed public snapshot with every GCP identifier replaced by a placeholder. It deploys into a fresh project:

  1. Enable the APIs and create a Terraform state bucket.
  2. Fill in infra/terraform.tfvars from the example.
  3. Create the Artifact Registry repo, then build and push the three images.
  4. terraform apply, add the Kalshi API key to Secret Manager, and smoke-test.

The full ordered steps are in the README.
